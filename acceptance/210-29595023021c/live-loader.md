Ten real dynamic-loader arms were executed twice, once against the pinned head 29595023021c1f1d6bc6b1e75307301a34bd0cd6 and once against the pinned base ae3077a09f2dcc7970721f7d06c6022de49ced1f, for both launchers (llama-server and whisper-server). In every arm the product's own child-env builder produced the environment, a real process was spawned with it and its environment was read back from that child's /proc/<pid>/environ, and CUDA resolution was performed by the real glibc loader /lib64/ld-linux-x86-64.so.2 running a compiled ELF whose NEEDED entries are the exact SONAMEs libcudart.so.13 and libcublas.so.13. The vendored cudart/cublas files are byte-identical copies of the host toolkit's CUDA 13 payloads (sha256 matched), and each arm's resolved object path was read back from the loader child's own /proc/<pid>/maps.

HEAD: on the unpatched host (ldconfig readable, its cache naming a system CUDA 13) both launchers withheld the vendored dir and the child mapped the system /usr/local/cuda-13.1 payloads. With the cache unreadable (real RLIMIT_NPROC=0 blocked exec) both launchers appended the vendored dir last and the child mapped both CUDA objects from the vendored dir (rc 0); the same binary with the appended dir removed failed rc 127. The exact-SONAME vendored shape loads when forced (rc 0), and the payload-only shape (fully-versioned filenames, no SONAME entry) fails rc 127 while the helper refuses that dir. In the synthetic arch-dir sub-arms, an unreadable cache with the arch dir populated yielded 'already provides' and a withhold, while the same dir emptied yielded 'not provided', an append, and a vendored resolution.

BASE: it never appends any vendored dir in any arm, so every unreadable-cache arm fails rc 127 for both launchers, while its host-default and system-precedence arms do resolve the system objects. The base/head difference is therefore exactly the append the change introduces, with the withhold behaviour preserved.

## Limitations

- No real /usr/local/lib/ollama tree exists on this host (and a root-owned system dir cannot be populated here), so the vendored tree was synthesized inside the arm workspace and reached through the module's documented roots override. The bytes placed in it are the host's real CUDA 13 payloads (sha256-identical to /usr/local/cuda/targets/x86_64-linux/lib), not stubs.
- The arch-specific default dir used by the two synthetic precedence sub-arms is a workspace directory assigned to the loader default-dir list; the real /lib/x86_64-linux-gnu and /usr/lib/x86_64-linux-gnu dirs were only detected and reported, not modified. The sub-arm result is a synthetic-shape limitation of this host, and the real-host cache arm is reported separately and unpatched.
- The ldconfig-unavailable arms enforce RLIMIT_NPROC=0 to make exec genuinely fail; that is a real kernel-enforced failure, but it is not a disk-image with ldconfig removed. To keep the loader run consistent with that state, those arms pass ld.so's own documented --inhibit-cache.
- The restricted loader arms deliberately search only the binary dir plus whatever the product appended, modelling a host with no system CUDA toolkit; the unrestricted host arms use the child's real LD_LIBRARY_PATH unchanged. Neither arm ran a GPU kernel: no CUDA workload, no device initialization and no inference was executed, so nothing here attests to GPU runtime behaviour.
- A 'pass' here means the change does what it claims for the loader search path and the child environment; it is not a substitute for the GPU/model-run validation a real Ollama CUDA 13 host could provide.
- The prior stage directory validation/live-loader/ contains only plan.json (no stage or result manifest was produced by that attempt), so there are no earlier stage observations to merge; nothing was erased.
- The per-arm working trees under scratch/<revision>/ (the synthesized install and vendored trees and the CUDA payload copies) were removed after their evidence JSON was copied into artifacts/. The recorded library paths therefore name directories that no longer exist; the arm JSON under artifacts/ holds the full observations, and the harness plus the consumer source are preserved so the run can be reproduced.
